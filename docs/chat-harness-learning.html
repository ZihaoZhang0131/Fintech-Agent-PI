PI RESEARCH AGENT / CHAT HARNESS / 2026-09-10

从聊天接口
到可靠的 Agent 运行时

这次改造最重要的不是“换了一个 Agent 类”，而是把执行权、状态所有权和恢复责任从浏览器的一次请求中拆了出来。

本文以你的投研 Agent 当前工作树为依据，解释为什么这样改、每层代码负责什么、哪些时序最容易出错，以及怎样亲手验证。只讨论聊天模式，Workflow 是另一套系统。

建议学习时间：第一遍 30–45 分钟建立模型；第二遍 60–90 分钟对照源码；第三遍完成练习。文中的教学简化代码都明确标注，不应直接替换生产代码。

00 / LEARNING OBJECTIVES看完以后，要能解释什么？

“听懂术语”不等于“能够做出一个可靠 Agent”。用下面三层目标检验自己：

层级你应当能做到可观察的证据
L1 · 讲得清区分 Thread、应用 Turn、Pi 内部轮次；解释刷新为什么不应等于停止。不看文档，用一张图说明浏览器、Runtime、Pi 和 SQLite 的关系。
L2 · 查得到从一个问题定位到正确文件与状态，而不是只看聊天气泡。找到一轮任务的状态、原始消息、事件序号，以及补充消息的消费状态。
L3 · 验得了设计断线、重复提交、晚到输入、压缩失败和进程退出测试。写出“操作 → 预期 → 断言”，并在隔离测试中证明行为。

阅读路线：先读 01–03，再按 04 → 05 → 06 追踪一条普通消息；最后再看压缩、补充和恢复。不要一开始就在 600 多行的工具事件映射里迷路。

如果你已经会写 HTTP 接口但第一次接触 Agent 工程，优先注意本文反复出现的四个问题：谁拥有任务？哪里是事实来源？什么时候算成功？失败后凭什么恢复？

01 / THE CHANGE三个 P0，本质上是三个“所有权”问题

P0原来的脆弱点这次的落点
执行生命周期Web 路由创建 Agent；请求取消与 Agent 中止绑在一起。Local Runtime 持有运行中的任务，浏览器只提交操作和订阅状态。
上下文生命周期模型历史主要从浏览器消息重建，显示记录不等于完整工具协议；缺少持续预算管理。保存 Pi 原始 Session；每次模型请求前检查预算；压缩与原文存储分离。
用户输入生命周期运行中输入受限；即便加一个发送按钮，也不能解决消息何时被接纳、是否丢失的问题。持久化 pending 输入；通过 steer 接入；在落入 Session 时原子标记 consumed。

不要把这次改造理解成“ReAct 换成 Plan-Execute”

用工程视角看，聊天仍然采用模型决定下一步 → 调用工具 → 把工具结果交回模型 → 继续或结束的循环。可以把它理解为 ReAct 风格的工具调用循环，但不意味着我们读取或持久化了模型的内部思维链。

这次没有把聊天强行变成“先生成完整 DAG，再逐节点执行”的固定流程。改的是循环外面的执行与状态管理：AgentHarness承接 Pi 的会话和事件能力，应用再补上持久化、HTTP、权限快照和前端同步。

模型回答的问题

“下一步查什么？要调用哪个工具？现有证据够不够？”

属于任务推理与工具选择。

Harness 回答的问题

“任务存在哪里？断开后谁继续跑？结果什么时候落盘？用户如何停止？”

属于确定性运行机制。

对照旧版：git show HEAD:app/api/chat/stream/route.ts 中的 new Agent、history.map、request.signal；对照新版：manager.mjs 与 agent.ts。HEAD 若以后提交更新，旧版对照需换成改造前的提交。

02 / VOCABULARY先分清六个对象

对象本项目中的含义常见误解
Thread一个聊天会话，绑定项目；可包含多轮任务。不是系统线程，也不是一个永久占用 CPU 的线程。
应用 Turn一次 Start，或一次 Continue 创建的执行单元；有 id、状态、输入与配置。不等于一次模型 HTTP 请求。
Pi 内部轮次Harness 内部模型与工具之间的推进过程；一次应用 Turn 可以包含多次推理。看到多次 turn_end，不代表应用应该立即结束。
SessionPi 的结构化历史与树形记录抽象；包含消息、工具调用/结果、压缩记录等。不只是“用户和助手说过的话”两列文本。
Item / 显示投影面向 UI 的消息与工具卡片状态；目前快照仍使用完整会话显示投影。工具卡上写“完成”不等于拿到了完整原始结果。
Event一次可回放的状态变化，带 Thread 内单调递增的 seq。事件 ID 不是任务 ID；回放事件不是重跑任务。
Thread A：研究某家公司
  ├─ 应用 Turn 1：分析现金流
  │    ├─ 模型请求 1 → 调用数据工具
  │    ├─ 模型请求 2 → 阅读结果
  │    └─ 接纳补充 → 模型请求 3 → 最终回答
  ├─ 应用 Turn 2：输出报告（被中断）
  └─ 应用 Turn 3：继续上次任务
       previousTurnId → Turn 2

常驻的是谁？Node 的 ChatSessionManager 拥有执行生命周期。Session 有空闲缓存，但每个应用 Turn 会重新组装 Harness 与工具。不是让一个 Agent 实例永远不销毁，也不是把“持久化”误认为“只放在 Map 里”。

04 / REQUEST PATH点击“发送”后发生了什么？

假设用户输入：“分析这家公司的现金流”。我们沿一条真实代码路径往下走。

  1. 前端准备一次明确的操作

    sendMessage() 根据状态选择 Start、Steer 或 Continue。prepareChatSubmission()保存这次操作的 path、body 与请求 ID，重试时复用。

  2. 服务端预留 Turn

    manager.start()校验输入和配置，再调用 store.reserve()。同一 Thread 的同一个 requestId 命中旧记录时返回旧 Turn；内容不同则 409。

  3. 先保存，再开始后台执行

    事务中写入 queued Turn、用户显示消息与 queued 事件。Manager 把执行状态放进 runs Map，再启动 execute(state)。

  4. HTTP 返回“已接收”

    http.mjs 返回 202。它不等待模型最终回答，也不把任务的生命周期绑在响应流上。

  5. 恢复上下文、解析能力

    Manager 取得项目、Session 和模型引用；prepareChatAgent()加载 Skills、工具和提示词，组装 Harness。API Key 在本机模型层解析，不跟配置一起持久化。

  6. 在模型调用前挂好约束

    注册 context hook 检查预算，注册 tool_result hook 管理大结果，然后把 Turn 置为 running 并执行 bundle.run()。

  7. 边执行边记录

    Pi 原始消息写入 SessionStorage；显示事件经 store.emit()同步更新 UI 投影和事件表，再通知订阅者。

  8. 完成并释放活动执行状态

    确认没有晚到输入后结束 Trace，再标记 completed。finally 中清理定时器与当前 runs 项。Session 可以继续留在空闲缓存中。

教学简化 · manager.start 的骨架
const reserved = store.reserve(threadId, requestId, input, config);
if (reserved.duplicate) return reserved.turn;

const state = { turn: reserved.turn, controller: new AbortController() };
runs.set(threadId, state);
state.done = execute(state); // 保存 Promise，不 await 最终答案
return reserved.turn;       // HTTP 层据此返回 202

关键：这里“没有 await”并不等于随便放飞异步任务。Manager 仍保存 state.done，停止、删除和关闭进程时都能等待它收尾。普通 Serverless 请求中简单写一句 void run()，并不能自动得到同样的生命周期保证。

为什么请求 ID 之外，还要保存内容 hash？

去重是在识别“同一次操作重试”，不是在识别“两句话一样”。两次真正独立的用户请求可以文本相同，但应有不同 ID；同一个 ID 却改了参数，应拒绝而不是悄悄执行不同任务。

第一次：requestId = req-01，input = 分析现金流 → 创建 Turn T1
重试：  requestId = req-01，input = 分析现金流 → 返回 T1
冲突：  requestId = req-01，input = 删除文件   → 409
新请求：requestId = req-02，input = 分析现金流 → 空闲时创建 T2

定位：store.reserve()；唯一约束 UNIQUE(thread_id,request_id)；hash 的输入包括 input、config、previousTurnId 和 operation。

05 / SOURCE OF TRUTH有数据库，不代表保存了足够的东西

同一轮任务，有三种不同的记录

记录用途不能替代什么
Pi Session给下一次推理恢复完整结构：角色、工具参数、toolCallId、结果、检查点。不能直接等同于紧凑好读的聊天 UI。
显示投影聊天文本、工具卡片、审批状态、耗时、Trace 链接。“调用成功”这样的摘要不能代替模型需要的原始结果。
Trace观察调用过程、耗时、用量与错误，沿用项目原有脱敏与展示逻辑。Trace 有展示与裁剪目的，不应冒充完整的会话恢复存储。

比如 UI 只显示“读取财务数据成功”。下一轮用户问“刚才现金流的单位是什么”，模型需要真实结果中的单位，不是“成功”二字。

教学示例 · 结构化消息与配对关系
// assistant：模型要求执行一个工具
{ role: "assistant", content: [
  { type: "toolCall", id: "call-7", name: "query_local_database",
    arguments: { sql: "SELECT year, cashflow FROM finance" } }
] }

// toolResult：必须能对应到那次调用
{ role: "toolResult", toolCallId: "call-7",
  toolName: "query_local_database", isError: false,
  content: [{ type: "text", text: "2025 年经营现金流 100，单位：亿元" }] }

七张新表，加一张原有兼容表

表主要职责排查时问它什么
chat_threads项目、当前 Turn、配置与 seq。这段聊天属于哪个项目？最近推进到哪里？
chat_turns输入、状态、幂等键、配置、恢复关系。任务结束没有？是不是某次重试？
chat_session_entries追加 Pi Session 记录。模型究竟看过什么？工具实际返回什么？
chat_items显示消息与工具卡片投影。该应用 Turn 有哪些显示记录？
chat_eventsThread 内有序的变化事件。断开以后错过了哪些变化？
chat_inputs补充输入及其消费状态。用户补充是待处理、已入上下文，还是被取消？
chat_results超大工具结果原文与所属 Thread。预览省略的部分如何找回？
chat_conversations原有完整显示投影，继续用于兼容现有 UI。刷新后页面应该显示哪些气泡和工具卡片？

现在很多业务字段存在 JSON body 中，关键查找字段单独建列。这样迁移成本低，但不意味着所有查询都已做成高度规范化或高吞吐设计。

为什么使用一个小事务？

假设补充输入已经写进 Session，但 consumed 状态还没更新时进程退出。重启后它会仍显示 pending，可能再次投递。反过来先写 consumed 再存消息，则可能“状态显示已处理，实际上下文没有”。

// 教学简化：这几件事必须一起成功或一起失败
BEGIN IMMEDIATE;
  INSERT INTO chat_session_entries (...);
  UPDATE chat_inputs SET body = '... consumed ...' WHERE id = ?;
  UPDATE chat_conversations SET body = '... 新投影 ...' WHERE id = ?;
  INSERT INTO chat_events (... input_status ...);
COMMIT;
// 事务提交以后，才向内存 Session 及订阅者发布。

BEGIN IMMEDIATE 提前取得写事务所需的锁；异常时执行 ROLLBACK。注意：事务里都是本机数据库操作，不把模型或网络请求放进这个事务，否则会长时间占锁。

WAL、缓存和备份各自负责什么？

  • WAL：SQLite 的写前日志模式，有利于本机读写并存和崩溃恢复；它不是云备份，也不能抵抗磁盘丢失。
  • Session 缓存：减少重复加载；空闲超过 30 分钟、且不在活动 Turn 中时才允许清理。缓存丢失后以 SQLite 重建。
  • pre-harness 备份：首次建立新表前用 VACUUM INTO 生成一致性备份；不是每轮自动生成的新快照。
  • 文件权限 0600：限制其他本机账户直接读取数据库；不等于加密。

“先持久化再可见”有范围。这里说的是关键应用事件和 Session 追加路径。模型的完整 assistant 消息在消息结束时进入 Session；流式文本以显示事件分批落盘。进程被杀时，最后一小段尚在 100ms 缓冲里的文本可能尚未持久化。不要把它理解为逐 token、零损失保证。

06 / RECONNECTSSE 是通知通道，不是任务本体

当前实现不是“浏览器接收所有增量并独立重建整个 UI”的方案，而是：先读权威快照，用 SSE 得知变化，再合并刷新显示投影。

  1. useChatThread()先 GET 快照，同时取得 seq，例如 40。
  2. 连接 /events?afterSeq=40，只需要关注后面的事件。
  3. 收到新事件后，约 100ms 合并一次快照刷新，避免为每个细碎 token 拉一次完整状态。
  4. 新快照若已经包含到 seq 46，之后看到 ≤46 的通知可以忽略。
  5. SSE 出错时关闭旧订阅，约 1 秒后重新走“快照 → 订阅”。取消的是这个订阅，不是后台 Turn。
id: 41
data: {"threadId":"T","turnId":"R","seq":41,"type":"delta","text":"现金流"}

id: 42
data: {"threadId":"T","turnId":"R","seq":42,"type":"turn_status","status":"completed"}

// 每条 SSE 消息由空行分隔；这些只是通知示例。

为什么断线期间不会错过最终状态？

最终状态不仅存在于网络里，也写进数据库。重连先拿快照，就算完成事件已经发生很久，仍能看到 completed。这解决的是“重新看到结果”，不是重新做一遍计算。

为什么慢浏览器可以被主动断开？

如果 res.write() 告诉服务端背压过大，当前实现销毁该 SSE 响应，让客户端以后用快照/游标补齐。执行任务不用等待某个浏览器缓慢接收所有字节。

目前的取舍：复用现有工具卡片投影，减少两端 reducer 不一致的风险；代价是长对话仍可能频繁搬运完整投影。后端消息分页已经存在，但前端还没有虚拟列表和纯增量渲染。可靠性改进不应被夸大成所有性能问题都已解决。

时序推演：选择一个容易混淆的场景

纯本地教学演示，不连接你的 Agent，不创建任务。逐步观察“执行状态”和“观看状态”何时一起变、何时不变。

1 / 4 · 任务正在运行

Runtime：running；浏览器：已订阅。执行权在 Runtime。

07 / CONTEXT BUDGET为什么不能一直把全部历史发给模型？

持久化解决“历史还在不在”，并不解决“下一次能不能全部塞进模型”。模型窗口有限，工具结果、系统提示和工具 schema 也都占空间。

用字母表示当前代码中的预算：

C = model.contextWindow
M = model.maxTokens（缺失或 0 时使用 16384）
R = min(M, 16384, floor(0.2 × C))         // 输出预留
S = min(floor(0.8 × C), C - R)           // 自动压缩阈值
H = C - R                               // 硬预算
K = min(20000, floor(0.2 × C))           // 近期保留目标

例：C=32000，M=4096
R=4096，S=25600，H=27904，K=6400

字符估算中，非 Latin-1 字符按约 1 token，其他字符约 0.35 token；它是保守启发式，不是模型 tokenizer。估算还会和 Pi 的估算、最近有效的 provider usage 比较取较保守的结果。

预算计算器

复现 budgets 的数值规则及普通自动路径，不调用模型。假定不存在“相同上下文上次压缩失败”的跳过记录；手动强制压缩也不适用此判断。

输出预留 R4,096
压缩阈值 S25,600
硬预算 H27,904
近期目标 K6,400
超过压缩阈值，但尚未达到硬预算：尝试压缩；失败时可保留原上下文。

为什么要给输出预留空间？

如果窗口装满输入，就算模型“知道怎么回答”，也没有足够空间输出。提前整理上下文，还能为新的工具结果和用户补充留出缓冲，而不是等服务商报 context length 错误才临时救火。

定位：budgets()、count()、transform()。近期目标还会根据中文/JSON 与 Pi 估算的比值校正，不等于固定保留最后 6400 个字符。

08 / COMPACTION压缩改变工作上下文，不删除档案

三个层次不能混在一起

持久历史：所有已保存的原始 Session entries 仍在 SQLite
                ↓ 构建
工作上下文：最近摘要 + 保留尾部 + 必需 Skill 调用/结果
                ↓ 转换
模型请求：系统提示 + 工具 schema + 本次实际发送的消息

你可以把它理解为：原始研究材料留在档案柜里，桌面上放一份工作摘要和当前必需材料。桌面收拾过，不等于档案销毁了。

为什么不直接调用 agent.compact()？

当前 Pi 0.83 的 Harness compact()要求空闲状态，而我们要在一轮任务内部、下一次模型请求前自动整理。于是接在 context hook 上，调用公开的准备、摘要生成和 Session 检查点接口。

实际接入点 · manager.mjs
bundle.agent.on("context", e => context.transform(e.messages));
bundle.agent.on("tool_result", e => boundToolResult(store, t.threadId, e));
  1. 计算本次上下文占用；未越阈值时直接返回。
  2. 把上次压缩留下的 retainedTail 展开为仅供准备阶段使用的记录。
  3. 调用 prepareCompaction()选择旧消息与保留尾部。
  4. 调用公开 compact()生成摘要，传入当前模型集合、取消信号及专门摘要要求。
  5. 补回需要保留的 Skill 调用/结果配对，检查压缩后的预算。
  6. 成功后追加 compaction entry，再从 Session 构建新上下文。

摘要不能只是“用户在研究某公司”

投研任务中，遗漏一个单位或日期就可能改变结论。因此摘要指令明确要求保留：目标、用户约束、来源 URL、数据日期、单位和口径、纠正、已否定假设、已执行动作、未知结果、待解决问题和下一步。

不合格摘要：用户正在研究 A 公司，已经查了很多财务数据。

更有用的摘要：
目标：分析经营现金流的持续性，不给买卖建议。
事实：2025 年经营现金流为 100 亿元；来源为已读取年报 URL。
纠正：用户要求用合并报表口径，不能混用母公司口径。
已完成：数据文件已保存至 outputs/cashflow.json。
未知：报告写入曾中断，需核验文件存在与内容，不可直接声称完成。
下一步：解释现金流与利润差异，保留缺失数据清单。

这是教学示例，不是项目中的真实公司数据。摘要质量仍依赖模型；“指令要求保留”不等于数学上保证永不遗漏。

二次压缩为什么容易丢上下文？

Pi 的检查点把“上一轮未摘要的尾部”放在 retainedTail 中，getBranch()可以在这个检查点停止向前追溯。如果下一次只处理检查点后的消息，上一段尾部既没有进入旧摘要，又可能被新处理跳过。

第一次：A B C D E F → [摘要(A B C)] + [尾部 D E F]
新增：  G H
第二次真正应该处理：[旧摘要] + D E F + G H
错误做法：          [旧摘要] + G H      ← D E F 被漏掉

当前适配把 retainedTail 临时展开。带 :tail: 的虚拟 ID 只用于准备，不应当被冒充为持久树上的真实节点 ID。检查点保存真实的 retainedTail 内容。升级 Pi 版本时，要重新验证这一兼容层，而不是机械复制。

为什么压缩完仍可能“看起来很大”？

旧 assistant 的 usage 记录描述的是压缩前某次请求。若拿它继续判断新上下文，会立刻再次触发压缩。usageCutoff在估算时排除旧用量基准，但没有删除原始计费用量记录。

压缩失败的处理

  • 生成失败或取消：不追加半成品检查点。
  • 未到硬预算：允许继续使用原上下文；同样估算大小的失败上下文在本 ContextManager 中不会反复压缩。
  • 已到硬预算，或手动强制压缩失败：明确结束为失败/中断，保留历史供用户处理。
  • 必需 Skill 内容本身太大：可能仍无法压缩到预算内；保留约束并失败，比悄悄丢掉约束更诚实。

大工具结果：存原文，给预览，按需分页

普通结果的 content超过约 8000 估算 tokens 时，用随机 UUID 保存完整结果，模型先得到最多 6000 个 JavaScript 字符长度单位的预览和 resultId，随后按需调用 read_chat_tool_result。offset/length 实现使用字符串 slice，不是 UTF-8 字节偏移；遇到补充平面字符时也不等于用户感知字符数。

结果表的查询同时要求 resultId 和 threadId，所以知道别人的 resultId 也不能通过这个工具读取别的聊天。分页默认 4000，最大 6000；返回 nextOffset 帮助继续读取。工具 details 为兼容原 UI 仍保留，不应宣称所有结果字段都已经完全外置。

09 / STEERING & RACES“能继续打字”只是最表面的一步

真正的问题是：用户刚发出的补充，能否确认它被接收？何时进入上下文？如果碰巧在任务结束那一瞬间到达怎么办？

状态准确含义不代表
pending应用已接收并持久化，等待接纳。模型已经读到或理解了。
consumed对应用户消息已进入 Pi Session，消费状态一起提交。模型一定服从、答案一定包含要求。
cancelled显式停止时未消费的当前轮输入被取消。已经送到模型的要求能被撤回。

正常路径

用户发送补充
  → 检查 expectedTurnId 与活动 Turn 是否一致
  → SQLite 写 pending
  → 准备阶段先入 state.pending，运行阶段投递 agent.steer(text)
  → Pi 在可处理边界取走输入
  → SessionStorage 追加用户消息 + 原子更新 consumed
  → UI 收到状态变化

steer()不是“立刻打断当前工具并插入文字”。应用把输入排入 Pi 的队列，具体接纳发生在运行循环的边界；工具已经开始后的取消语义是另一件事。

竞态一：补充内容的类型匹配错了

Pi 的 user content 可以是结构化数组，不一定是字符串。若直接做 pending.text === entry.message.content，已入 Session 的补充可能永远匹配不上，最后又被当成“晚到未消费”重复处理。

实际逻辑节选 · 先规范化文本，再找到待消费项
const content = typeof entry.message.content === "string"
  ? entry.message.content
  : entry.message.content
      .filter(c => c.type === "text")
      .map(c => c.text).join("");

return state.delivered.find(i =>
  i.status === "pending" && i.text === content
);

找到后，存储层给 entry 记录 chatInputId并执行前面讲过的事务。注意当前仍以文本和队列顺序做匹配，不是 Pi 原生携带应用 inputId；同文多条、重复恢复等复杂情况仍值得继续加测试。

竞态二：刚返回“已接收”，Pi 却已经 idle

Pi：最后一次检查队列 → agent_end / settled → 已空闲
用户：                         发来补充 → 应用接受
结果：agent.steer() 可能因为 idle 而拒绝

Manager 的补偿：
prompt 返回后再看 delivered 中仍 pending 的输入
  → 先把第一条作为 user 消息追加
  → 在同一个应用 Turn 里再次 prompt
  → 继续处理剩余补充

这就是为什么“模型返回最终消息”不一定等于“应用 Turn 马上 completed”。应用还要检查自己已经接受的输入有没有遗留。测试中专门在 settled事件触发补充，而不是靠随意 sleep 去碰运气。

竞态三：Start 重试变成了 Steer

第一次 POST 已被服务端接受，但浏览器没拿到确认；此时 SSE 先告诉浏览器“正在运行”。如果重试时重新按 busy 状态选择端点，就会把原问题再次作为补充发送。

prepareChatSubmission()冻结了端点 + body + 请求 ID。所以重试 Start 还是 Start。收到确认后先清空已提交草稿，再更新显示；后续快照失败不再伪装成提交失败。真正的 400/404/409 拒绝则保留草稿，并清理不再适用的重试记录。

工程方法：发现一个 race，不要只加一个 if。先画出两条交错的时间线，再定义“不允许发生的结果”，最后写能够确定性制造这个交错的测试。

10 / INTERRUPTION & RECOVERY刷新、停止、重启、继续，是四件事

动作谁改变任务结果
刷新 / 订阅断开浏览器连接Runtime 继续执行；重新读取状态。
Interrupt当前 Turn 的 AbortController向模型/工具传递取消；等待收尾后 interrupted。
Runtime 重启执行进程和内存状态初始化 recover 把遗留 queued/running 标成 interrupted；不自动跑。
Continue新建应用 TurnpreviousTurnId 指向旧轮；以保存的 Session 恢复工作。

停止不是单纯把按钮改成灰色

页面“停止”
  → POST /turns/:turnId/interrupt
  → state.controller.abort()
  → bundle.run 内的 abort 监听
  → agent.abort()
  → 下游模型与工具感知 signal
  → await state.done
  → 返回最终 Turn 状态

既有 Bash、文档、MCP、子 Agent 的取消链继续复用。对模型解析和主 Agent MCP 发现增加了可传入的 signal。需要等待的清理是否及时，仍取决于每个下游实现，不能承诺所有外部动作“瞬间回滚”。

为什么恢复时不自动重放“没完成的调用”？

假设工具已经成功写文件，但进程在保存结果前退出。数据库里没有 toolResult，实际文件却可能已经存在。没有结果只能证明“我们没记录到结果”，不能证明“动作没有发生”。

工具调用已记录 → 文件确实写入 → 进程退出 → toolResult 没落盘
                                      ↑
                      这是结果未知窗口，不是确定失败

repair(session)对缺结果调用补上明确的错误消息：“结果未知，先核验实际状态，禁止直接重放”。新的推理从这份诚实上下文开始。它并没有一个通用的外部事务系统，也没有给文件写入自动加上 exactly-once 语义。

一个实践细节：为什么会多出一个“关闭旧连接”的修复？

开发热重载要求旧进程退出后新进程再启动。即使业务已经关闭，遗留 SSE/HTTP 连接也可能让退出一直等待。关闭流程在应用和 MCP 收尾后调用 server.closeAllConnections()，避免旧代理连接卡住开发服务。

顺序很重要：先结束应用任务，再关闭残留连接。解绑项目时也要先中断该项目的聊天任务，再移除注册信息，否则下游取消请求可能因项目已经找不到而失败。

11 / BOUNDARIES能力没有被换掉，执行边界被明确了

  • 原有工具：文件、数据库、文档、Web 搜索、Bash、MCP 和委派工具的主要业务逻辑继续复用。
  • 原有权限：Bash 的自动/逐条确认、项目沙箱/完整权限仍是原来的产品选择；运行中的配置不会随另一个页面瞬时改变。
  • Node Skill 加载：新的 skills.ts用文件系统读取 bundled Skill 和本地覆盖，不依赖 Web 打包器的 ?raw 导入。
  • 凭据边界：config.mjs重建允许的嵌套结构，阻止请求里的 apiKey、headers 等任意字段直接进入配置快照。用户自己写进问题或提示词的秘密不因此自动消失。
  • 旧历史：没有完整工具结果就如实标为 legacy，委派卡片只导入成历史事实，不伪装成已核验执行轨迹。
  • 旧写入：迁移后拒绝浏览器整包覆盖消息；仍支持按约定更新会话控制元数据。
  • 旧执行入口：返回 410 提示刷新，防止两个入口各自执行一次。

Prompt 不等于权限系统。“不要访问其他文件”是模型指令；真正阻止越界访问还要靠现有工具路径校验、执行沙箱、服务端能力筛选等机制。新增 Harness 不是一个新的通用安全沙箱。

练习六 · 自己写一个失败用例规格（20 分钟）

选择“压缩摘要生成到一半取消”或“工具成功、结果落盘前退出”。先不写代码，写五行：前置状态、故障注入点、用户应看到什么、数据库应保留什么、绝不能出现什么。

验收标准 / 参考答案

压缩取消：旧 leaf 不变，无半成品检查点，原文仍在。工具结果未知：不能生成虚假的成功结果，不能由恢复引擎直接重放旧工具调用，应保留明确的不确定性。下一步要验证真实目标，而不是仅靠重试。

14 / LIMITS这是一轮 P0 改造，不是完美终点

学习最重要的一步，是能同时说清“这次解决了什么”和“证据还没有覆盖什么”。以下是从当前实现可以看到的边界：

  1. 单 Runtime 假设。同 Thread 串行依赖本机 Manager 与同步预留流程；没有跨进程租约、分布式队列或多副本 owner 选举。不要直接拿来水平扩容。
  2. 整份显示投影仍会读写。事件通知可靠性提高了，但高频快照和大 JSON 的成本尚在。后续可测量后再考虑客户端增量 reducer、虚拟列表和归档。
  3. 模型可控，不代表模型可靠。steer 被 consumed 只能证明已入 Session；摘要要求保留来源，也不能替代摘要质量评测。
  4. 未知结果仍需核验。恢复机制不直接重放旧动作，但模型仍可能决定调用工具。外部系统要严格幂等，需要工具层幂等键、操作账本或业务级核验。
  5. 流式最后小段可能未落盘。100ms / 8192 字符批量缓冲是性能与粒度取舍；突然断电并不是完整逐 token 日志测试。
  6. 结果表没有自动清理策略。大结果原文会增长；保留时长、大小配额、压缩率与清理机制还需后续设计。
  7. 文本匹配与继承输入值得加测。目前 pending 恢复投递仍保留旧 turnId；显式停止的清理查询按当前 Turn 取 pending。若恢复后再次在消费前停止，旧 Turn 上继承的 pending 是需要补充验证/完善的边界，不能无条件宣称所有队列都已取消。
  8. 恢复配置的产品取舍。resume()复用旧 Turn 的 config。即使用户此时选了另一个模型，“继续”也不是自动用新选择；若要改变模型恢复，需要明确设计接口，而不能只改前端下拉框。
  9. 超大 Skill 可能阻断。目前倾向完整保留已加载 Skill 配对。复杂会话中保留量可能过大，需要未来决定哪些资源仍有效，而不是无限积累。

这些是学习时应识别的后续工程题，不是本 HTML 悄悄实现的新功能。本次文档工作不修改聊天运行代码，也不改 Workflow。

15 / SELF-CHECK不用看代码，回答这八个问题

1. SSE 连接断了，为什么任务还能运行？

执行被 Runtime 的 Manager 拥有；SSE 只是一个可销毁的订阅，关闭它不调用任务的 AbortController。

2. Map 里有一个 Promise，为什么还需要 SQLite？

Map 与 Promise 只在进程存活时有意义。重启后需要输入、状态、原始 Session、结果和 pending 记录来知道发生过什么；数据库不能恢复一个旧 Promise，但能为显式新执行提供依据。

3. “toolCall 已记录但 toolResult 缺失”意味着工具失败吗？

不意味着。它可能没执行，也可能执行成功却来不及记录。必须表达结果未知并核验，不能伪造失败或成功来简单重试。

4. 为什么不能只保存最终回答？

后续推理可能需要原始参数、结果、单位、来源和 toolCallId 配对。最终回答是提炼后的展示内容，不能无损重建这些信息。

5. consumed 为什么要和 Session entry 放进同一个事务？

避免一边成功另一边失败，造成“已经投递却仍 pending”或“标了 consumed 却没有消息”。

6. 为什么压缩后不能继续用旧 usage 直接判断大小？

旧 usage 测的是压缩前那次请求。上下文已经改变，继续套用可能立即再次触发压缩。它应留作历史计量，但不应成为新上下文的旧高水位。

7. 为什么 Continue 不是把旧状态从 interrupted 改回 running？

新执行拥有独立 ID、开始时间、Trace 和生命周期，通过 previousTurnId 关联旧轮。这样能保留中断事实，而不是抹掉历史。

8. 这次为什么没有重写一套 Agent Loop？

Pi 已提供工具循环、会话与事件接口。本项目需要补的是产品级状态、持久化、交互和恢复边界。复用成熟循环，才能把工程精力放在真实缺口上。

最后，用一段话复述这次改动

“原来的聊天执行依赖 Web 请求，并从显示历史重建模型上下文。这次把执行移到本机 Manager，使用 Pi AgentHarness 驱动原有工具；SQLite 保存应用 Turn、原始 Session、补充输入和事件。浏览器通过快照与 SSE 查看进度，刷新不再等于取消。运行中补充通过持久队列进入安全处理边界；上下文接近预算时用检查点压缩。中断后不盲目重跑，用户 Continue 才从保存的事实开始新轮次。”
